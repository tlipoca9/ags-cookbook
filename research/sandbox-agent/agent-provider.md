# Choose the baseline agent and model-provider contract

Research ticket: [Choose the baseline agent and model-provider contract](https://github.com/tlipoca9/ags-cookbook/issues/6)

Research date: 2026-09-01

Primary source snapshots: Sandbox Agent `bbc195cc3fb5a1dd9cb05d8437442768c511e17e`; OpenAI Codex `e017e93aceafb2fe04bed1c926e448a5fb4f913d` (`rust-v0.152.0` was the current release); Tencent Cloud documentation retrieved 2026-09-01.

## Executive recommendation

Use **Sandbox Agent agent id `codex` with Tencent Cloud TokenHub model id `hy3` over the OpenAI Responses API** as the single golden path.

This satisfies the TokenHub preference without a downstream patch:

1. Sandbox Agent natively recognizes and installs the `codex` agent and launches its Codex ACP adapter ([source](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/server/packages/agent-management/src/agents.rs#L20-L112), [install source](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/server/packages/agent-management/src/agents.rs#L1384-L1433)).
2. Tencent Cloud publishes a first-party Codex recipe for `model_provider = "hy3-tokenhub"`, model `hy3`, base URL `https://tokenhub.tencentmaas.com/v1`, an environment-backed key, and `wire_api = "responses"` ([Tencent Codex guide](https://cloud.tencent.com/document/product/1823/133532)).
3. Current Codex source supports user-defined providers with `base_url`, `env_key`, and only the `responses` wire protocol; `chat` is rejected ([provider source](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/model-provider-info/src/lib.rs#L61-L119), [configuration source](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/config/src/config_toml.rs#L153-L168)).
4. TokenHub documents native Responses support for `hy3`, Function Calling, and the Guangzhou `/v1/responses` route ([protocol matrix](https://cloud.tencent.com/document/product/1823/130079), [model list](https://cloud.tencent.com/document/product/1823/130051)).

**Decision status:** evidence-backed configuration decision, but not yet a credentialed end-to-end result. A no-secret local probe proved that Codex accepted the contract and requested exactly `https://tokenhub.tencentmaas.com/v1/responses`; the intentionally invalid placeholder key received the expected HTTP 401. The blocked Shanghai prototype must still perform the real task/SSE/pause-resume validation with a scoped test key.

## Exact configuration contract

### Fixed values

| Item | Golden-path value |
| --- | --- |
| Sandbox Agent agent id | `codex` |
| Model provider id (Codex-local name) | `hy3-tokenhub` |
| TokenHub model id | `hy3` |
| Wire protocol | OpenAI Responses |
| Base URL | `https://tokenhub.tencentmaas.com/v1` |
| Effective inference route | `POST https://tokenhub.tencentmaas.com/v1/responses` |
| Provider credential variable | `HY3_API_KEY` |
| Authentication | `Authorization: Bearer $HY3_API_KEY` (generated by the Codex provider client from `env_key`) |
| Sandbox Agent session model field | **Omit it**; Codex reads `model = "hy3"` from `config.toml` |
| Coding mode for the later HTTP journey | `auto`, not Sandbox Agent's default `read-only`, because the acceptance task must edit files |

Tencent documents Guangzhou and Singapore as separate TokenHub sites: Guangzhou uses `https://tokenhub.tencentmaas.com`, Singapore uses `https://tokenhub-intl.tencentmaas.com`; keys are not interchangeable, and the service does not support cross-site key use ([API usage](https://cloud.tencent.com/document/product/1823/130078), [language-model overview](https://cloud.tencent.com/document/product/1823/130079)). The golden path fixes the **Guangzhou** site. Do not dynamically select a base URL or silently fail over to the Singapore site.

### Non-secret image configuration

Create `/root/.codex/config.toml` (or the runtime user's corresponding `~/.codex/config.toml`) in the image:

```toml
model_provider = "hy3-tokenhub"
model = "hy3"

[model_providers.hy3-tokenhub]
name = "Hy3 via TokenHub"
base_url = "https://tokenhub.tencentmaas.com/v1"
env_key = "HY3_API_KEY"
wire_api = "responses"
```

This is configuration, not a patch. The file contains no credential. Inject `HY3_API_KEY` only into the running AGS Deployment environment; do not put it in the image, repository, HTTP payload, captured output, or shell history.

The Tencent guide also shows `disable_response_storage = true`. It is intentionally omitted above because that key is absent from the current Codex `ConfigToml` and generated schema at commit `e017e93` ([current config type](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/config/src/config_toml.rs#L153-L540), [schema](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/core/config.schema.json)). No replacement is needed for endpoint selection or authentication.

### Runtime environment

Required for the provider contract:

```bash
HY3_API_KEY=<runtime-injected-tokenhub-key>
```

`OPENAI_API_KEY` and `CODEX_API_KEY` are **not** required on this path. Avoid setting them so Codex cannot accidentally fall back to OpenAI credentials. Sandbox Agent server authentication and AGS gateway credentials are separate contracts and are not redefined here.

Use a TokenHub key created in the Guangzhou site with access limited to `hy3` and an appropriate quota. Tencent documents that TokenHub keys are long-lived, can be model-scoped, IP-scoped, and quota-limited, and should be rotated ([API Key management](https://cloud.tencent.com/document/product/1823/130090)). The exact key lifetime, quota, and IP allowlist remain deployment/security choices for the credential ticket, not this report.

### Session creation behavior

The later raw-HTTP contract should select `agent: "codex"` and `mode: "auto"`, but omit a session-level model override. Conceptually:

```json
{
  "agent": "codex",
  "mode": "auto"
}
```

The exact endpoint and complete request body belong to the separate raw HTTP/SSE ticket. Omission of the model field is deliberate: the checked Sandbox Agent snapshot publishes a static Codex model catalog containing OpenAI model ids only, while the Codex process itself reads the custom `hy3` provider and model from `~/.codex/config.toml` ([Sandbox Agent Codex page](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/docs/agents/codex.mdx), [catalog](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/scripts/agent-configs/resources/codex.json), [fallback logic](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/server/packages/sandbox-agent/src/router/support.rs#L116-L147)).

## Compatibility limitations

1. **Static Sandbox Agent metadata is wrong for this custom provider.** `/v1/agents` may report `credentialsAvailable: false` because it checks only OpenAI-named variables for Codex, and model discovery will list the committed OpenAI model ids rather than `hy3`. Treat those two metadata fields as known false negatives; do not use them as the readiness gate. The actual readiness probe must complete a Codex turn.
2. **Do not send a session-level `model: "hy3"` until separately validated.** Codex and Claude do not report ACP `configOptions`, so Sandbox Agent uses a hard-coded fallback catalog ([source note](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/server/packages/sandbox-agent/src/router/support.rs#L223-L237)). The image-level Codex config is the supported selection seam.
3. **Codex lacks first-party metadata for `hy3`.** The no-secret probe logged: `Model metadata for 'hy3' not found. Defaulting to fallback metadata; this can degrade performance and cause issues.` Tencent documents the actual window as 256k context, 192k maximum input, and 128k maximum output ([model list](https://cloud.tencent.com/document/product/1823/130051)). Do not promise optimal compaction, token budgeting, or maximum-context behavior until measured.
4. **No Responses WebSocket contract.** Leave `supports_websockets` unset/false; this scenario uses HTTP/SSE. TokenHub documents SSE for streaming Responses, while Codex enables WebSocket only when a provider explicitly declares it ([Codex provider source](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/model-provider-info/src/lib.rs#L134-L150), [Tencent Responses documentation](https://cloud.tencent.com/document/product/1823/133813)).
5. **TokenHub Responses capabilities are model-dependent.** `hy3` is listed as native Responses, but fields, reasoning output, cache usage, and sampling behavior can still differ by model; Tencent explicitly documents such variation ([overview](https://cloud.tencent.com/document/product/1823/130079)). The generic compatibility-mode limitations in the Responses guide apply to converted models, not necessarily to native `hy3`, and must not be overgeneralized ([compatibility guide](https://cloud.tencent.com/document/product/1823/133813)).
6. **Region/site coupling remains.** The AGS Deployment target is `ap-shanghai`, but the selected TokenHub service site is Guangzhou. Tencent provides no Shanghai TokenHub base URL in the checked docs. Network reachability, latency, egress policy, and key/site compatibility must be tested from the actual Deployment.
7. **Version pinning is delegated, not waived.** Sandbox Agent's installer follows the latest Codex release when no version is supplied. The image-contract ticket must pin a Codex release that retains the checked custom-provider/Responses behavior; do not use an unversioned `install-agent codex` in the reproducible image.
8. **Security boundary.** Sandbox Agent states that provider credentials passed into a sandbox are visible to the agent and everything in that sandbox ([credential docs](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/docs/llm-credentials.mdx#L37-L47)). This report chooses an environment variable because the ticket requires it; it does not approve sharing one unrestricted key among untrusted tenants.

## Rejected alternatives

### Codex + OpenAI API key (accepted contingency, not the golden path)

If the real Shanghai probe disproves the remaining TokenHub inference, use:

- agent id: `codex`
- model id: `gpt-5.3-codex`
- endpoint: Codex's built-in OpenAI provider/default API behavior; do not set a custom base URL
- required variable: `OPENAI_API_KEY`
- remove the `hy3-tokenhub` provider selection from `config.toml`

Sandbox Agent publishes `gpt-5.3-codex` as its Codex default and documents `OPENAI_API_KEY` for Codex ([Codex docs](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/docs/agents/codex.mdx), [credential docs](https://github.com/rivet-dev/sandbox-agent/blob/bbc195cc3fb5a1dd9cb05d8437442768c511e17e/docs/llm-credentials.mdx#L27-L35)). It is not selected now because the evidence threshold for the preferred TokenHub path is met.

### OpenCode + TokenHub

Tencent provides a first-party OpenCode configuration with `@ai-sdk/openai-compatible`, `deepseek-v4-pro`, and the same TokenHub base URL ([Tencent OpenCode guide](https://cloud.tencent.com/document/product/1823/130936)). Sandbox Agent also supports agent id `opencode`. This path is valid but adds an OpenCode provider/auth-store seam when Tencent already documents direct Codex Responses configuration, so it is unnecessary for a single-agent golden path.

### Pi + community TokenHub extension

A community Pi provider exists, but its own README states that it is unofficial and not affiliated with Tencent Cloud ([repository](https://github.com/huangmeme/pi-tencent-tokenhub-provider/tree/09426a33ba73d1dcdee1376f56e0a2ebbf22e131)). It does not meet the first-party evidence bar when direct Tencent Codex documentation is available.

### Token Plan + old Codex Chat wire protocol

Reject this for the golden path. Tencent's Token Plan Codex guide requires Codex `0.80.0` or earlier because that service path was Chat-only ([Token Plan Codex guide](https://cloud.tencent.com/document/product/1823/130071)), while current Codex source rejects `wire_api = "chat"` ([OpenAI source](https://github.com/openai/codex/blob/e017e93aceafb2fe04bed1c926e448a5fb4f913d/codex-rs/model-provider-info/src/lib.rs#L57-L89)). TokenHub's Responses endpoint avoids that downgrade.

## Residual unknowns and validation gates

These are gaps, not implied approvals:

- No real TokenHub credential was available, so no authenticated model response, tool call, file edit, token usage, or SSE completion event was observed.
- No Sandbox Agent process was installed locally, so the Codex ACP adapter plus custom-provider combination has not yet been exercised end to end.
- The exact Codex version in the future CCR image is unresolved by this ticket. The checked current release source is `rust-v0.152.0`; the local endpoint probe used installed `codex-cli 0.144.5`.
- TokenHub `hy3` behavior under Codex's multi-turn coding loop, compaction fallback metadata, approval flow, and long-lived paused workspace has not been measured.
- Egress, DNS, latency, and service-site behavior from an `ap-shanghai` AGS Deployment to the Guangzhou TokenHub endpoint remain empirical questions.
- The correct operational policy for TokenHub key scope, quota, IP allowlist, rotation, and revocation belongs to the credential/security ticket.

## Implications for the blocked Shanghai prototype

The provider decision no longer blocks image and HTTP contract work. The prototype can bake the non-secret Codex TOML, inject only `HY3_API_KEY` at runtime, create a `codex` session without a model override, and use coding mode `auto`.

It must not claim success merely because agent metadata reports installation or credentials. The promotion gate is one authenticated turn that:

1. reaches the Guangzhou TokenHub Responses endpoint from `ap-shanghai`;
2. emits parseable Sandbox Agent SSE through terminal completion;
3. invokes coding tools and changes a deterministic workspace file;
4. resumes the same Sandbox Agent session/workspace after pause; and
5. captures only redacted status/model/route evidence.

If that gate fails because of the custom-provider seam rather than AGS lifecycle behavior, switch the prototype once to the documented contingency (`codex` + `gpt-5.3-codex` + `OPENAI_API_KEY`) and record the failure; do not add a proxy, patch Codex, patch Sandbox Agent, or silently change agents within this ticket's contract.
